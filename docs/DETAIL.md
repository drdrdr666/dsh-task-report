# 任务档案

一次任务交出去以后，最容易丢的不是代码，是这几样东西：做到哪了、动过什么、还要用户做什么、哪些没验证、这趟到底换来了什么。它们通常只存在于对话正文里，会话一断就归零。

这个插件把它们沉淀成工作区里的 **`.dsh-task/<slug>.md`**：随工作区存活，可提交进仓库，可跨会话读回，也能直接交给别人接手。

## 能做什么

| 动作 | 用途 |
|---|---|
| `open` | 建立任务档案，记录目标（建议用用户原话），并设为当前任务 |
| `update` | 增量补记：阶段、已完成项与证据、阻塞、待用户操作、副作用、未验证项、决策、价值收口 |
| `close` | 收尾校验：缺项直接返回 `missing` 清单，不写入收尾时间；补齐后才生成最终档案 |
| `show` | 读回当前任务的完整档案 |
| `list` | 列出工作区里所有任务及其阶段 |

## 收尾会强制检查哪些内容

这不是宽松的记录器。`close` 要求以下几项显式交代过，**没有也要写“无”**：

- 目标原话
- 至少一条已完成项，且带验证证据
- `value.did`（一句话做成了什么）与 `value.helped`（对用户解决了什么）
- `userActions`（待用户操作）与 `unverified`（未验证项）—— 必须显式传，空数组也会被接受
- `sideEffects`（副作用清单）

缺项时 `close` 不落收尾时间，只回一份清单，避免"看起来完成了"。

## 档案结构

生成的 Markdown 固定十节：目标 / 已完成（含证据）/ 进行中 / 阻塞 / 待用户操作 / 副作用清单 / 未验证与已知限制 / 决策记录 / 价值收口 / 下次入口。

副作用清单分五类：文件、系统设置、进程与端口、外部账号、凭据 —— 因为这几类最容易在下一次被忘掉。

## 用法

```
task_report(action:"open", slug:"my-task", goal:"用户原话")
task_report(action:"update", patch:{
  phase:"实现",
  done:[{what:"修掉了 X", evidence:"node tests/run.mjs 16 项通过"}],
  sideEffects:{processes:["起了本地代理 8899，已关闭"]}
})
task_report(action:"close", patch:{
  userActions:[{action:"重启宿主", why:"进程里仍是旧代码", ifNot:"修复不生效"}],
  unverified:["未在干净环境验证安装"],
  value:{did:"…", helped:"…", reuse:["tools/xxx.mjs 可复用"]},
  sideEffects:{files:["新增 lib/x.js"]}
})
```

## 限制

- 档案存在**工作区**里，不写入会话日志；换工作区就看不到旧任务。
- 不做自动采集：副作用、待办、证据仍需在过程中通过 `update` 记进去。插件保证结构完整，不保证内容诚实。
- 只记录，不代替验证：`done[].evidence` 是文字，插件不会去核对它是否真的跑过。
